## 0. 发布策略 (R2 新增 — 三段式发布)

R2 范围评估指出单次 v1.0.0 承载 3 大功能 + 3 项稳定性,工时 ~150h,风险高度集中。采用三段式渐进发布:

| 版本 | 内容 | 工时 | 风险 | 价值 |
|------|------|------|------|------|
| **v0.9.0** | F2 (新 Claim) + S0 + S1 | ~54h | 低 (纯 readonly 增强) | 立刻强化核心验证能力,获用户反馈 |
| **v0.9.5** | F3 (多本体) + S2 | ~42h | 中 (内存/桥接) | 解锁生物医学场景 |
| **v1.0.0** | F1 (写工具) + MCP annotations + 协议协商修复 | ~58h | 高 (定位变更) | 单独承载 "readonly → write" 语义跃迁 |

理由:
1. F2 零安全风险,应最快交付 — 延后等于让用户为写工具等 16 天才能用新 Claim
2. F1 最危险最复杂,单独发布可集中测试资源
3. v1.0.0 的 "1.0" 语义重大,应只承载定位变更

## 1. 定位演进 (R1 新增, R2 保留)

v0.x 系列的核心承诺是 "readonly MCP server for LLM agents"。v1.0.0 **不颠覆**这一承诺,而是演进为:

> **readonly-first + opt-in write**

- 默认行为不变: 不带 `--allow-write` 时, 服务器与 v0.8.4 完全一致
- 写能力是**可选叠加层**: `--allow-write` 启用时, 写操作在**编辑副本**上进行
- canonical 本体仅在显式 `ontology_commit` 时更新

## 3. F2: 新 Claim 类型 (v0.9.0 — P0 先做)

### 3.1 新增 5 种 Claim 类型 + 1 增强

| Claim 类型 | 验证内容 | 示例 | R1/R2 变更 |
|-----------|----------|------|-----------|
| `CLASS_RESTRICTION` | 基数限制 + 值限制 | "Pizza hasBase exactly 1 PizzaBase" | R1 API 修正 + R2 ELK guard |
| `PROPERTY_CHAIN` | 属性链蕴含 | "hasParent ∘ hasParent → hasGrandparent" | R1 API 修正 |
| `PROPERTY_CHARACTERISTIC` | 属性特征验证 | "hasBase is functional" / "hasChild is irreflexive" | R1 ELK guard + R2 矩阵修正 |
| `INVERSE_PROPERTY` | 逆属性关系 | "hasBase inverseOf isBaseOf" | R2 ELK guard |
| `NEGATIVE_ASSERTION` | 负属性断言 | "France is not locatedIn Germany" | R1 新增 + R2 ELK guard |
| `DATA_PROPERTY_ASSERTION` (增强) | 推理器支持 | "France hasPopulation 67000000" | - |

> Claim 类型总数: 14 → 19 (+5 新增 +1 增强)。`ANNOTATION_ASSERTION` 降级 v1.1.0, `HAS_KEY` 延后 v1.1.0。

### 3.2 CLASS_RESTRICTION 详细设计 (R1 API 修正 + R2 ELK guard)

```json
{
  "type": "class_restriction",
  "subject": {"iri": "http://example.org/Pizza"},
  "predicate": "hasBase",
  "restriction": {
    "kind": "cardinality",
    "value": 1,
    "filler": {"iri": "http://example.org/PizzaBase"}
  }
}
```

**验证逻辑** (R1 修正):
1. **断言检查**: 扫描 `AxiomType.SUBCLASS_OF` + `EQUIVALENT_CLASSES`, 过滤 `getSuperClass() instanceof OWLObjectMinCardinality / OWLObjectMaxCardinality / OWLObjectExactCardinality / OWLObjectHasValue / OWLObjectSomeValuesFrom / OWLObjectAllValuesFrom`
2. **推理检查**: `reasoner.isEntailed(df.getOWLSubClassOfAxiom(cls, restriction))` — R2 验证确认 API 正确
3. **反例检查**: `reasoner.isSatisfiable(df.getOWLObjectIntersectionOf(cls, df.getOWLObjectComplementOf(restriction)))` — false 等价 supported

**R2 新增 ELK guard**: cardinality/minCardinality/maxCardinality **不在 OWL 2 EL profile 内**, ELK 会抛异常。hasValue/someValuesFrom/allValuesFrom 在 EL 内,可正常推理。ELK + cardinality kind → 返回 `UNSUPPORTED_CLAIM_TYPE`。

### 3.3 PROPERTY_CHAIN 详细设计 (R3 API 重大修正)

**R3 代码验证发现**: R2 文档描述的 API 路径**完全错误**。OWL API 5.1.20 中:
- `getOWLSubObjectPropertyOfAxiom(List, OWLObjectPropertyExpression)` 重载**不存在** — 只有 `(OWLObjectPropertyExpression, OWLObjectPropertyExpression)` 二元形式
- `getOWLObjectPropertyChain(List<>)` 方法**不存在**于 `OWLDataFactory`
- 属性链公理由独立接口 `OWLSubPropertyChainOfAxiom` 表示,与 `OWLSubObjectPropertyOfAxiom` 是**不同的公理类型**

**R3 修正验证逻辑**:
1. **断言检查** (主路径): `ontology.getAxioms(AxiomType.SUB_PROPERTY_CHAIN_OF)` → 遍历 `OWLSubPropertyChainOfAxiom` → `ax.getSuperProperty().equals(superProp)` + `ax.getPropertyChain()` 逐元素匹配
2. **构造方法** (若需构建 axiom 对象): `df.getOWLSubPropertyChainOfAxiom(List<OWLObjectPropertyExpression> chain, OWLObjectPropertyExpression superProp)` — R3 验证此方法存在且签名正确
3. **推理检查**: 属性链几乎总是断言的(极少推理得出),仅走断言检查即可。未找到匹配 → UNKNOWN (非 CONTRADICTED)

**R3 实现建议**: 不需要 `checkAxiomEntailment`,直接扫描断言公理更简洁可靠。

### 3.4 PROPERTY_CHARACTERISTIC 详细设计 (R1 guard + R2 矩阵修正)

**R2 修正兼容性矩阵** — R1 误将 `symmetric` 标为 ELK 不支持,实际 symmetric 在 OWL 2 EL profile 内:

| 特征 | HermiT | ELK (OWL 2 EL) | Openllet | EL profile | R2 变更 |
|------|--------|-----------------|----------|------------|---------|
| functional | ✓ | △ 部分 | ✓ | ✓ 在 EL 内 | - |
| inverseFunctional | ✓ | ✗ guard | ✓ | ✗ 不在 EL | - |
| symmetric | ✓ | △ 有限 | ✓ | **✓ 在 EL 内** | **R2 修正: 不 guard** |
| asymmetric | ✓ | ✗ guard | ✓ | ✗ 不在 EL | - |
| reflexive | ✓ | ✗ guard | ✓ | ✗ 不在 EL | - |
| irreflexive | ✓ | ✗ guard | ✓ | ✗ 不在 EL | - |
| transitive | ✓ | ✓ | ✓ | ✓ 在 EL 内 | - |

**ELK guard 规则** (R2 修正): 仅对 inverseFunctional / asymmetric / reflexive / irreflexive (4 种, 非 R1 的 5 种) 返回 `UNSUPPORTED_CLAIM_TYPE`。functional / symmetric / transitive 正常验证。

### 3.5 NEGATIVE_ASSERTION 详细设计 (R1 新增 + R2 ELK guard + R3 API 修正)

**R3 API 修正**: `OWLDataFactory.getOWLNegativeObjectPropertyAssertionAxiom` 参数顺序是 `(OWLObjectPropertyExpression property, OWLIndividual subject, OWLIndividual object)`,**不是** `(subject, property, object)`。R2 文档未提及参数顺序,R3 补充。

**R2 新增 ELK guard**: `NegativeObjectPropertyAssertion` **不在 OWL 2 EL profile 内**, ELK 会抛异常。ELK 时跳过 `isEntailed` 调用,仅走断言检查 + 反例检查路径。

**R3 实现建议**: ELK guard 不需要预判 profile,用 `try { reasoner.isEntailed(axiom); } catch (Exception e) { return UNSUPPORTED_AXIOM_TYPE; }` 更简洁 — 统一适用于所有 ELK 不支持的公理类型。

### 3.6 INVERSE_PROPERTY (R2 ELK guard + R3 实现简化)

**R2 新增**: `InverseObjectProperties` 不在 OWL 2 EL profile 内。ELK guard: 走断言检查路径 (`ontology.getInverseObjectPropertyAxioms(prop)`), 跳过 `isEntailed`。

**R3 实现简化**: 不需要单独的断言检查路径,统一走 `checkAxiomEntailment(df.getOWLInverseObjectPropertiesAxiom(p1, p2))` — asserted 快速路径 + try/catch isEntailed 即可覆盖所有情况。

### 3.7 R3 新增: 统一 checkAxiomEntailment 方法设计

**R3 重大架构修正**: R2 为 5 种新类型分别设计了断言检查 + 推理检查 + 反例检查的独立路径。R3 代码原型验证发现,**统一方法更简洁且更可靠**:

```java
// ReasonerService 新增接口方法
ServiceResult<EntailmentResult> checkAxiomEntailment(
    OWLOntology ontology, OntologyId ontologyId,
    OWLAxiom axiom, Optional<String> reasonerName);
```

**统一逻辑** (替代 R2 的 5 套独立逻辑):
1. **断言快速路径**: `ontology.containsAxiom(axiom)` → 返回 `ENTAILED, source="asserted"`
2. **推理路径**: `try { reasoner.isEntailed(axiom); } catch (Exception e) { return UNSUPPORTED_AXIOM_TYPE; }`
3. **ELK guard 统一**: 不需要按公理类型预判 EL profile,try/catch 自动处理所有 ELK 不支持的情况

**适用范围**: PROPERTY_CHARACTERISTIC / INVERSE_PROPERTY / CLASS_RESTRICTION / NEGATIVE_ASSERTION (4 种)。PROPERTY_CHAIN 仍走独立断言扫描路径 (§3.3)。

**R3 工时影响**: 5 种类型 × 独立逻辑 → 1 统一方法 + 1 独立扫描,F2 #3-7 工时可减少 ~4h (从 23h → ~19h)。

### 3.8 测试本体 (R1 新增, R2 工时修正, R3 策略修正)

**R3 策略修正**: R2 要求新建 `test/corpus/test-restrictions/source/test-restrictions.owl` (7h)。R3 原型验证发现**两段式测试策略更高效**:

1. **Stub 单元测试** (程序化构建最小本体): 在 `@BeforeEach` 中用 `OWLManager.createOWLOntologyManager()` + `df.getOWLDeclarationAxiom()` 构建仅含必要 Declaration + 1 个 SubPropertyChainOf 的最小本体。**优点**: 自包含、确定性、无需 Protégé、覆盖 verdict 映射逻辑。
2. **Pizza 集成测试** (复用现有 pizza.owl): pizza.owl 已含 `hasBase inverseOf isBaseOf`、`hasBase InverseFunctional`、`American SubClassOf hasTopping some MozzarellaTopping` — 覆盖 3/5 类型的 SUPPORTED 路径。**优点**: 真实 reasoner (HermiT) 端到端验证。

**R3 工时修正**: 7h → **3h** (无需手工编写 OWL 文件,程序化构建 + 复用 pizza)。

## 4. F3: 多本体联合推理 (v0.9.5 — P1 第二做)

### 4.1 设计理念

```
Agent: "验证 'Disease X has_phenotype Phenotype Y' 在 HPO+Mondo 联合本体中是否成立"
  → ontology_verify_claim(ontology_ids=["hpo", "mondo"], claim=...)
  → 系统自动构建只读联合视图
  → 跨本体推理验证
```

### 4.2 多本体加载 (R1 参数修正)

`ontology_ids: ["hpo", "mondo"]` 数组 (非逗号字符串)。解析层严格拒绝字符串形式或做归一化。

**R2 schema 约束** (MCP 合规): `verify_claim` 的 inputSchema 用 `oneOf` 表达 `ontology_id` (string) 与 `ontology_ids` (array) 二选一:
```json
{"oneOf": [
  {"required": ["ontology_id"]},
  {"required": ["ontology_ids"]}
]}
```
`ontology_ids` 优先; `ontology_id` 保留向后兼容。

### 4.3 F1 ontology_merge vs F3 OntologySet 边界 (R1 新增)

| | F1 `ontology_merge` | F3 `OntologySet` |
|---|---|---|
| **持久化** | 是, 写入 canonical, 加入 catalog | 否, 仅缓存, 会话内虚拟视图 |
| **安全模型** | 需要 `--allow-write` | 只读 |
| **缓存** | 走正常 OntologyCache | 独立 union cache (max 2, 60s TTL) |

### 4.4 跨本体验证

- **EntitySignatureCache** (R1 重构): `Set<String>` → `Map<iri, Set<ontologyId>>` 支持来源追踪
- **Catalog 旁路** (R1): 联合本体 IRI `owl4agents:union/<hash>` 跳过 catalog 检查
- **导入闭包**: `Imports.EXCLUDED`, 仅使用显式加载的成员本体

### 4.5 实体来源工具 (R1 新增)

`ontology_get_entity_provenance`: 参数 `entity_iri`, `ontology_ids` → 返回 `{"iri": "...", "source_ontologies": ["hpo"], "declared_in": "hpo"}`

### 4.6 对齐桥接 (R1 安全修正)

- 桥接公理**必须**提供 `evidence_source` 字段
- 默认仅允许 `skos:closeMatch` / `skos:exactMatch`
- `equivalentClasses` 需显式 `--allow-bridge-equivalence`
- 桥接公理在返回结果中高亮标记

### 4.7 联合本体内存管理 (R1 修正)

HPO 74MB + Mondo 236MB → 联合本体 ~1.5-3GB heap + 推理器索引 ~600-900MB = 峰值 ~6-8GB。

措施: 独立 cache (max 2, 60s TTL) + `-Xmx8g` 建议。

## 5. F1: 写工具 + 本体编辑 (v1.0.0 — P2 最后做)

### 5.1 设计理念 (R1 修正)

> Agent 能在**沙箱副本**内实验性编辑, 不污染 canonical 本体。commit 是显式的、可选的。

### 5.2 新增 MCP 工具 (8 个)

| 工具 | 功能 | 参数 | 安全约束 |
|------|------|------|----------|
| `ontology_add_axiom` | 添加公理 | ontology_id, axiom (结构化对象), dry_run? | 写前一致性检查; 不一致返回结构化冲突 |
| `ontology_remove_axiom` | 删除公理 | ontology_id, axiom, force? | 删前一致性检查 + 受保护公理需 force |
| `ontology_commit` | 提交编辑副本到 canonical | ontology_id, session_id | commit 后重分类 + 6 处缓存失效 |
| `ontology_merge` | 持久化合并两个本体 | source_id, target_id, merge_mode | 需 --allow-write |
| `ontology_export` | 导出本体 | ontology_id, format, output_path | output_path 限 workspace/exports/ |
| `ontology_diff` | 对比版本差异 | ontology_id, baseline_snapshot_id | - |
| `ontology_snapshot` | 创建快照 | ontology_id, snapshot_name | diff 存储 (非全量) |
| `ontology_list_session_edits` | 列出会话写操作 | ontology_id, session_id | 返回结构化数组 (非 JSONL 文本) |

工具总数: 56 readonly + 1 provenance + 8 write = **65**

### 5.3 结构化 axiom 参数 (R1 修正 + R2 schema 增强)

R2 MCP 合规: 用 `oneOf` 按 `axiom_type` 分支定义不同 shape, LLM 选择更准确:

```json
{"oneOf": [
  {"type":"object","required":["axiom_type","subclass","superclass"],
   "properties":{"axiom_type":{"const":"sub_class_of"},...}},
  {"type":"object","required":["axiom_type","classes"],
   "properties":{"axiom_type":{"const":"disjoint_classes"},"classes":{...}}}
]}
```

`axiom_type` 用 `enum` 列全部值。每类型在 `description` 里给最小 JSON 示例。

### 5.4 事务模型 (R1 架构修正 — copy-on-edit)

```
1. ontology_snapshot("before-edit")     → 创建 diff 基线
2. (系统) copyOntology(canonical, DEEP)  → 创建编辑副本
3. ontology_add_axiom(...)              → 在编辑副本上 applyChange
4. (自动) check_consistency(副本)        → 一致性验证
5a. 一致 → 返回成功, 副本保留 (未 commit)
5b. 不一致 → 丢弃副本, 返回结构化冲突详情
6. ontology_commit()                    → 序列化 + invalidate + 重分类
```

R2 验证确认: `OWLOntologyManager.copyOntology(orig, OntologyCopy.DEEP)` 存在; `OWLOntologyChange` 可序列化; AddAxiom↔RemoveAxiom 互换可实现反向 diff。

**R2 性能风险** (新增到 §8): Mondo 236MB deep copy ~5-15s + 推理器重建 ~10-30s = 单次编辑周期 15-45s。建议: 编辑副本按 ontology 缓存 (而非每次 add_axiom 都 deep copy), commit/rollback 时才创建/丢弃。

### 5.5 安全模型 (R1 增强)

- **opt-in**: `--allow-write` 标志
- **沙箱副本**: 编辑副本独立于缓存实例
- **显式 commit**: `ontology_commit` 提交
- **一致性护栏**: add + remove 均触发 checkConsistency, 返回 `{"conflicting_axioms": [...], "explanation": "..."}`
- **受保护公理**: `owl4agents.protected-axioms=file` 配置; 删除需 `force=true`
- **审计日志**: append-only JSONL, "写入后不修改" (不声称不可篡改)
- **快照上限**: 50 个或 500MB (diff 存储成本低)
- **路径遍历防护**: `WorkspaceSafety.checkExportPath()`

### 5.6 缓存失效链 (R1 补全 + R2 验证)

R2 代码验证确认 `shutdownReasoner()` (line 91-100) 确实遗漏 `reasoningReports` (line 28)。**R2 新增**: `shutdownAll()` (line 199-207) 同样遗漏, 需一并修复。

写操作 commit 后需失效:

1. `OntologyCache` — `invalidate()` 触发 reload ✓
2. `EntitySignatureCache` — listener 级联 ✓
3. `ReasonerServiceImpl.inferredHierarchyCache` (line 38) — listener 级联 ✓
4. `ReasonerLifecycleManager.reasoningReports` (line 28) — **R1 发现遗漏, R2 确认**: `shutdownReasoner()` + `shutdownAll()` 均需修复
5. `CatalogStore` 元数据 — commit 后 mtime/size 更新
6. 联合本体派生缓存 — 成员本体 commit 时级联失效 union cache (F3 #12 产物)

### 5.8 推理器并发安全 (R1 S0 前置 + R2 工时修正)

- **S0**: `OWLReasonerAdapter` 加 `ReentrantLock` 串行化推理调用

### 5.9 MCP 工具标注 (R2 修正 — 替代"工具分组")

**R2 关键修正**: R1 的"工具分组"概念在 MCP 2025-06-18 协议中**不存在**。`tools/list` 返回扁平 `Tool[]` 数组, 无分组字段。

**正确做法**: 使用 MCP 标准 `annotations` 字段 (协议原生机制):

```java
// 每个 Tool 的 annotations
{
  "readOnlyHint": true/false,        // true=只读, false=写
  "destructiveHint": true/false,     // ontology_remove_axiom = true
  "idempotentHint": true/false,      // ontology_export = true
  "openWorldHint": true              // 本体可被外部修改
}
```

- readonly 客户端的 `tools/list` **不返回写工具** (服务端过滤, 非协议分组)
- `--allow-write` 客户端看到全部 65 个, annotations 帮助 LLM 区分
- 主流客户端 (Cursor/Claude Desktop) 读取 annotations 在 UI 上区分只读/破坏性

### 5.10 MCP 协议修复 (R2 新增 — 3 项)

**R2 发现 3 项 MCP 协议问题, v1.0.0 必须修复**:

1. **协议版本协商缺失**: `McpServerAdapter.java:201` 硬编码 `PROTOCOL_VERSION = "2025-06-18"`, 不读客户端请求的 `protocolVersion`。修复: `buildInitializeResult` 读取客户端版本, 返回 min(客户端, 服务端) 版本。
2. **capabilities 不完整**: 仅声明 `tools: {}`。修复: 声明 `tools: {listChanged: false}` (v1.0.0 不支持运行时切换)。
3. **错误码不合规**: readonly 客户端调写工具 (不在其 tools/list 中) 应返回 JSON-RPC **-32601** (Method not found), 非 `isError: true`。修复: `buildToolsCallResult` 识别 `TOOL_NOT_FOUND` → -32601。
4. **inputSchema 缺 `required` 数组**: 现有 56 个工具均未设 `required`。修复: 为所有工具 (含现有 + 新增) 补充 `required` 数组。

**R2 新增 ErrorCodes** (扩展 `ErrorCode` 枚举):
- `TOOL_NOT_FOUND` → JSON-RPC -32601
- `PROTECTED_AXIOM` (删除受保护公理缺 force)
- `CONSISTENCY_REJECTED` (写前一致性检查失败)
- `SESSION_NOT_FOUND` / `SESSION_EXPIRED`
- `PATH_TRAVERSAL_REJECTED`
- `BRIDGE_FORBIDDEN` / `EVIDENCE_SOURCE_REQUIRED`

### 5.11 session_id 语义 (R2 新增)

**R2 澄清**: `session_id` (工具参数, 应用层编辑会话) 与 `Mcp-Session-Id` (HTTP header, 传输层会话) **完全不同**:
- `session_id`: 由服务端在首次 `ontology_add_axiom` 时生成并返回, 对应 `workspace/edits/<session>/` 副本, 可跨 MCP 传输会话存活
- `Mcp-Session-Id`: HTTP 连接标识, 30 分钟 TTL, 断线重连后变化
- stdio 客户端 (无 Mcp-Session-Id) 也能获得 `session_id`

### 5.12 审计日志返回格式 (R2 修正)

`ontology_list_session_edits` 返回**结构化数组** (非 JSONL 文本):
```json
{"edits": [
  {"timestamp": "...", "operation": "add_axiom", "axiom_before": null, "axiom_after": {...}, "status": "committed"},
  ...
], "total": 5, "truncated": false}
```

R2 建议: 审计日志文件本身适合用 MCP `resources` 协议暴露 (`resources/read`), 但 Resources 延后 v1.0.1。v1.0.0 仅用工具返回结构化摘要。
